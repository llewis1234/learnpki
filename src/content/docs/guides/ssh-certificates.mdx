OpenSSH has its own certificate format. Instead of copying public keys into every server's `authorized_keys`, servers trust one SSH CA. Users and hosts get short-lived certificates signed by it.

## The problem with plain SSH keys

Plain SSH keys trust individual keys, one at a time:

- **Every server** keeps an `authorized_keys` list. When someone leaves, you must find and remove their key everywhere.
- **Every client** keeps a `known_hosts` list. The first connection asks "Are you sure you want to continue connecting?" Almost everyone types `yes` without checking. That's trust on first use, and it's how a man-in-the-middle gets in.

SSH certificates replace both lists with two CA keys:

<Diagram kind="ssh" />

- The **user CA** signs user keys. Servers trust it with one line: `TrustedUserCAKeys`.
- The **host CA** signs server keys. Clients trust it with one line in `known_hosts`: `@cert-authority`.

An SSH certificate is not X.509. It's a public key plus a few fields, signed by the CA key: a key ID, a serial, **principals** (allowed login names or host names), a validity window and a few options.

:::note[Use the lab VM]
You'll run a second copy of `sshd` on port 2222, so the VM's normal SSH server isn't touched. The VM plays both the laptop and the server. On a host install, use Linux or WSL with `openssh-server` installed.
:::

## 1. Give your CA SSH keys

`step ca init --ssh` creates SSH CA keys at setup. Your CA already exists, so add them by hand.

Create the host CA key pair. Use your CA password when asked:

```sh title="terminal"
step crypto keypair $(step path)/certs/ssh_host_ca_key.pub $(step path)/secrets/ssh_host_ca_key
```

```text title="Expected output"
Your public key has been saved in /home/ubuntu/.step/certs/ssh_host_ca_key.pub.
Your private key has been saved in /home/ubuntu/.step/secrets/ssh_host_ca_key.
```

Create the user CA key pair the same way:

```sh title="terminal"
step crypto keypair $(step path)/certs/ssh_user_ca_key.pub $(step path)/secrets/ssh_user_ca_key
```

:::tip[Use the same password]
step-ca can unlock all its keys with one password at startup. Use your CA password for both SSH keys.
:::

Open `$(step path)/config/ca.json`. Add this block at the top level, next to `"db"`. On a host install, replace `/home/ubuntu` with your home folder:

```json title="ca.json (excerpt)"
"ssh": {
	"hostKey": "/home/ubuntu/.step/secrets/ssh_host_ca_key",
	"userKey": "/home/ubuntu/.step/secrets/ssh_user_ca_key"
},
```

Allow your admin provisioner to sign SSH certificates:

```sh title="terminal"
step ca provisioner update admin@example.com --ssh
```

```text title="Expected output"
✔ CA Configuration: /home/ubuntu/.step/config/ca.json

Success! Your `step-ca` config has been updated. To pick up the new configuration SIGHUP (kill -1 <pid>) or restart the step-ca process.
```

Restart step-ca so it loads the new keys. Then ask it for its SSH CA keys:

```sh title="terminal"
step ssh config --roots
```

```text title="Expected output"
ecdsa-sha2-nistp256 AAAAE2VjZHNhLXNoYTItbmlzdHAyNTYAAAAIbmlzdHAyNTYAAABBBK2Ba+EiOYgU6HyYChOxbONwDdBKuJ0ATHmekUw6Dz2zPkDim+cz+/6xh2gEV++y8zRRcg9RFbppsJsMOkcIZ3Y=
```

That's the **user** CA public key. `step ssh config --host --roots` prints the host CA key.

## 2. Give the server a host certificate

On the server, sign its existing ECDSA host key. The certificate lists the names clients will use:

```sh title="terminal"
sudo step ssh certificate --host --sign \
  --principal localhost --principal host.example.com \
  host.example.com /etc/ssh/ssh_host_ecdsa_key.pub \
  --ca-url https://localhost:9000 --root $(step path)/certs/root_ca.crt \
  --provisioner admin@example.com
```

`--sign` means "sign this existing public key", so no new key is made. `--ca-url` and `--root` matter because `sudo` runs as root, which has no step config of its own.

```text title="Expected output"
✔ Provisioner: admin@example.com (JWK) [kid: g1zyOj-wl88rXBet9_rLLiMIvmqgERXB07sYMELbX4c]
✔ CA: https://localhost:9000
✔ Certificate: /etc/ssh/ssh_host_ecdsa_key-cert.pub
```

Read it with OpenSSH's own tool:

```sh title="terminal"
ssh-keygen -L -f /etc/ssh/ssh_host_ecdsa_key-cert.pub
```

```text title="Expected output"
/etc/ssh/ssh_host_ecdsa_key-cert.pub:
        Type: ecdsa-sha2-nistp256-cert-v01@openssh.com host certificate
        Public key: ECDSA-CERT SHA256:jXBUH7RDoDyzaLbsVtY4hEZp9ZkAZMqU/nJnkbA1xPM
        Signing CA: ECDSA SHA256:HmV4Pul5scja+zF/KBrXfqox0PRCKCv0d6XByH+tmig (using ecdsa-sha2-nistp256)
        Key ID: "host.example.com"
        Serial: 6867231075775752962
        Valid: from 2026-11-21T02:29:11 to 2026-12-21T02:30:11
        Principals: 
                localhost
                host.example.com
        Critical Options: (none)
        Extensions: (none)
```

Host certificates default to 30 days. Run the same command again before it expires. For hands-off renewal, step-ca's SSHPOP provisioner lets a host renew with `step ssh renew`, using its current certificate as proof.

## 3. Configure sshd to use both

Save the user CA key where sshd can read it:

```sh title="terminal"
step ssh config --roots | sudo tee /etc/ssh/ssh_user_ca.pub
```

Create a config file for the lab. Keep it out of `/etc/ssh/sshd_config.d/`, because your normal SSH server reads every file there:

```text title="/etc/ssh/pki-lab-sshd.conf"
TrustedUserCAKeys /etc/ssh/ssh_user_ca.pub
HostCertificate /etc/ssh/ssh_host_ecdsa_key-cert.pub
PidFile /run/sshd-pki-lab.pid
Include /etc/ssh/sshd_config
```

- `TrustedUserCAKeys` accepts any user certificate signed by this CA.
- `HostCertificate` makes sshd present its certificate to clients.
- `PidFile` keeps the lab server's process ID apart from your normal server's.
- `Include` pulls in everything else from your normal config. The lab lines come first because sshd keeps the first value it reads for most settings.

Only the lab server loads this file, so your normal SSH server never trusts the lab CA.

Test the config:

```sh title="terminal"
sudo sshd -t -f /etc/ssh/pki-lab-sshd.conf && echo "sshd config OK"
```

```text title="Expected output"
sshd config OK
```

On a host install, you might see `Missing privilege separation directory: /run/sshd` instead. Create the folder with `sudo mkdir -p /run/sshd`, then test again. The lab VM creates it at boot.

Start a second sshd on port 2222 with the lab config:

```sh title="terminal"
sudo /usr/sbin/sshd -f /etc/ssh/pki-lab-sshd.conf -p 2222
```

Create a local account for Alice to log in to:

```sh title="terminal"
sudo useradd -m -s /bin/bash alice
```

Alice has no password and no `authorized_keys`. The certificate is the only way in.

## 4. Get a user certificate

Make a folder for the lab's SSH files. It keeps the lab key and the lab's trust apart from your own `~/.ssh`:

```sh title="terminal"
mkdir -p ~/pki-lab/ssh && cd ~/pki-lab/ssh
```

Ask for a certificate for Alice:

```sh title="terminal"
step ssh certificate alice@example.com id_ecdsa
```

Choose a password for the new private key, then enter the provisioner password.

```text title="Expected output"
✔ Provisioner: admin@example.com (JWK) [kid: g1zyOj-wl88rXBet9_rLLiMIvmqgERXB07sYMELbX4c]
✔ CA: https://localhost:9000
✔ Private Key: id_ecdsa
✔ Public Key: id_ecdsa.pub
✔ Certificate: id_ecdsa-cert.pub
✔ SSH Agent: yes
```

If no `ssh-agent` is running, the last line shows an error instead. That's harmless. The files are on disk.

The private key is protected by the passphrase you chose. Keep it that way. The certificate is public, but the key is not.

```sh title="terminal"
ssh-keygen -L -f id_ecdsa-cert.pub
```

```text title="Expected output"
id_ecdsa-cert.pub:
        Type: ecdsa-sha2-nistp256-cert-v01@openssh.com user certificate
        Public key: ECDSA-CERT SHA256:IqSH8Vw/ewAlX3ryB55V9e9xJFKskkoY8apos+i+B58
        Signing CA: ECDSA SHA256:6HSyylWcY50sc2bjZfWhviLUaMe2pgyHXWCbDEM6gOA (using ecdsa-sha2-nistp256)
        Key ID: "alice@example.com"
        Serial: 1262158180302151276
        Valid: from 2026-11-21T02:29:11 to 2026-11-21T18:30:11
        Principals: 
                alice
                alice@example.com
        Critical Options: (none)
        Extensions: 
                permit-X11-forwarding
                permit-agent-forwarding
                permit-port-forwarding
                permit-pty
                permit-user-rc
```

Three things to notice:

- **Principals** are `alice` and `alice@example.com`. step derived them from the email. The server lets this certificate log in only as a listed principal.
- **Valid** for 16 hours, the default for user certificates. Tomorrow, Alice gets a new one. Nobody cleans up old keys.
- **Signing CA** is the user CA, not your X.509 intermediate. SSH and X.509 trust are separate.

## 5. Trust the host CA on the client

Make a `known_hosts` file for the lab with one line. It says: "for these host names, trust any host certificate from this CA."

```sh title="terminal"
echo "@cert-authority [localhost]:2222,*.example.com $(step ssh config --host --roots)" > known_hosts
```

`[localhost]:2222` is how OpenSSH writes a host on a non-standard port. `*.example.com` covers every server you'll add later.

Now tell ssh to use the lab files. Create a client config in the same folder:

```text title="~/pki-lab/ssh/config"
Host localhost 127.0.0.1
    Port 2222
    IdentityFile ~/pki-lab/ssh/id_ecdsa
    IdentitiesOnly yes
    UserKnownHostsFile ~/pki-lab/ssh/known_hosts
```

- `IdentityFile` picks Alice's key. ssh loads `id_ecdsa-cert.pub` next to it automatically.
- `IdentitiesOnly yes` stops ssh from trying your other keys.
- `UserKnownHostsFile` uses the lab's trust, not `~/.ssh/known_hosts`.

## 6. Log in

`-F config` makes ssh read only this file:

```sh title="terminal"
ssh -F config alice@localhost whoami
```

ssh asks for your key's passphrase. That unlocks the key on your laptop. It is not a server password.

```text title="Expected output"
Enter passphrase for key '/home/ubuntu/pki-lab/ssh/id_ecdsa':
alice
```

No account password. No "Are you sure you want to continue connecting?" Both sides proved themselves with certificates.

Add `-v` to see it happen:

```sh title="terminal"
ssh -F config -v alice@localhost whoami
```

```text title="Expected output (excerpt)"
debug1: Server host certificate: ecdsa-sha2-nistp256-cert-v01@openssh.com SHA256:jXBUH7RDoDyzaLbsVtY4hEZp9ZkAZMqU/nJnkbA1xPM, serial 6867231075775752962 ID "host.example.com" CA ecdsa-sha2-nistp256 SHA256:HmV4Pul5scja+zF/KBrXfqox0PRCKCv0d6XByH+tmig valid from 2026-11-21T02:29:11 to 2026-12-21T02:30:11
debug1: Host '[localhost]:2222' is known and matches the ECDSA-CERT host certificate.
debug1: Found CA key in /home/ubuntu/pki-lab/ssh/known_hosts:1
...
debug1: Offering public key: /home/ubuntu/pki-lab/ssh/id_ecdsa ECDSA-CERT SHA256:IqSH8Vw/ewAlX3ryB55V9e9xJFKskkoY8apos+i+B58 explicit agent
debug1: Server accepts key: /home/ubuntu/pki-lab/ssh/id_ecdsa ECDSA-CERT SHA256:IqSH8Vw/ewAlX3ryB55V9e9xJFKskkoY8apos+i+B58 explicit agent
```

The first two lines are the host check. The last two are the user check.

## Break it

### Log in as someone else

Create a second account:

```sh title="terminal"
sudo useradd -m bob
```

Try to log in as Bob with Alice's certificate:

```sh title="terminal"
ssh -F config bob@localhost whoami
```

```text title="Expected output"
Permission denied, please try again.
Permission denied, please try again.
bob@localhost: Permission denied (publickey,password).
```

The signature is valid, but `bob` isn't a principal in the certificate. Principals are how SSH certificates do authorization.

### Connect by a name nobody vouched for

Connect by IP address with strict checking on:

```sh title="terminal"
ssh -F config -o StrictHostKeyChecking=yes alice@127.0.0.1 whoami
```

```text title="Expected output"
No ECDSA host key is known for [127.0.0.1]:2222 and you have requested strict checking.
Host key verification failed.
```

Your `@cert-authority` line covers `[localhost]:2222` and `*.example.com`, and the host certificate lists `localhost` and `host.example.com`. Neither covers `127.0.0.1`, so the client falls back to plain host keys. Without `StrictHostKeyChecking`, you'd get the old "Are you sure?" prompt. In a certificate setup, that prompt means something is wrong.

If the CA line did cover the address, OpenSSH would still refuse, with `Certificate invalid: name is not a listed principal`. Both the client's pattern and the certificate's principals must match.

### No host CA trust at all

Move the lab's `known_hosts` file out of the way:

```sh title="terminal"
mv known_hosts known_hosts.off
```

Connect with strict checking:

```sh title="terminal"
ssh -F config -o StrictHostKeyChecking=yes alice@localhost whoami
```

```text title="Expected output"
No ECDSA host key is known for [localhost]:2222 and you have requested strict checking.
Host key verification failed.
```

The host certificate only helps clients that trust the host CA. Put the file back:

```sh title="terminal"
mv known_hosts.off known_hosts
```

## Clean up

In the lab VM, you can skip this. Deleting the VM removes everything. On a host install, undo the changes this lab made.

Stop the lab sshd, using its PID file:

```sh title="terminal"
sudo kill $(cat /run/sshd-pki-lab.pid)
```

Remove its config, the user CA key and the host certificate:

```sh title="terminal"
sudo rm /etc/ssh/pki-lab-sshd.conf /etc/ssh/ssh_user_ca.pub /etc/ssh/ssh_host_ecdsa_key-cert.pub
```

Remove the two lab accounts and their home folders:

```sh title="terminal"
sudo userdel -r alice
```

```sh title="terminal"
sudo userdel -r bob
```

Your own `~/.ssh` was never changed. The lab files stay in `~/pki-lab/ssh` until you delete them.
